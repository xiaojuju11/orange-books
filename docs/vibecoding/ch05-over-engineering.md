# 第 5 章 Agent 天生过度设计

> 它按“教科书最佳实践”狂做加法，而你的需求往往只要 20 行。

## 为什么需要它

你让它在前端加一个头像上传按钮。

半分钟后，它交出了一整套令你倒吸一口凉气的工程结构：
- 一个 `AvatarUploadService` 抽象接口
- 两个实现类（`LocalAvatarUploader`、`OssAvatarUploader`）
- 一个 `AvatarUploaderFactory` 工厂类
- 一个事件订阅总线 `UploadEventEmitter`
- 三个关联配置文件，外加四百行代码

而你真正的诉求仅仅是：**点击选一张图片，POST 发送到现有接口，页面转圈显示上传中，完成展示新头像。**

这不是模型水平不行，恰恰是因为它**训练数据里见过了太多完整的工业级开源项目**。它本能地认为“好代码就必须分层、必须抽象、必须为未来的各种可能性预留扩展”。

在软件工程中，这种现象被称为著名的**第二系统效应（Second-System Effect）**：当系统准备做一个新功能时，总试图把过往所有的理念、理想架构和未来扩展一次性塞进去。

在传统开发中，程序员会被工期、产品经理和 Code Review 强行压住；但在 AI 辅助编程里，**模型天生不会踩刹车**。如果没有一套体系化的工程减法，AI 会在一夜之间把你的轻量级项目堆砌成寸步难行的“过度设计屎山”。

## 术语表（人话翻译）

| 术语 | 人话白话 | 生活类比 |
| :--- | :--- | :--- |
| **过度设计 (Over-Engineering)** | 为“可能永远用不上”的未来提前造一大堆抽象轮子 | 刚租了一间单间，非要在房门上装三道防盗门和虹膜锁 |
| **最小实现 (Minimal Implementation)** | 解决当前核心痛点的最短代码路径，拒绝预支复杂度 | 先买一张能吃饭的书桌，别在客厅起地基盖餐厅 |
| **第二系统效应** | 本能地试图在一次迭代中把所有设计模式一次补齐 | 刚学了炒菜，做个西红柿炒蛋非要摆上法餐五道盘子 |
| **三板斧减法** | 事前约束、事后减法、规则固化的全周期控量机制 | 买菜前列清单、结账前掏出不要的、立家规不买多余零食 |

## 治理过度设计的“三板斧”

对付 AI 的过度设计，不能靠随缘提醒，必须在工作流中建立标准“三板斧”：

### 第一斧：事前约束（派活时明确最小实现）

在最初发送任务委托时，必须在提示词中直接把刹车踩死。直接使用以下固定约束模块：

```text
【实现原则】
1. 采用最直接的“最小实现（Minimal Implementation）”，只解决本次需求，不要考虑任何未提及的扩展性。
2. 严禁造轮子：能用项目中现有的工具函数和依赖，就绝对不引入新的第三方库。
3. 严禁无意义的过度抽象：能写成一个简单函数的，严禁引入类、接口、工厂或策略模式。
```

这三句话能直接挡掉 AI 80% 以上“顺手为你大肆封装”的加法冲动。

---

### 第二斧：事后减法（功能跑通后追击一轮审查）

当第一版代码写完、功能初步跑通之后，**千万不要立刻收工**！紧接着追加一轮自我审查对话：

```text
看一遍你刚才写下的这套实现：
1. 哪些代码和文件是本次需求根本用不到的？
2. 哪些抽象层或接口目前只有唯一的实现类？
3. 哪些逻辑是重复造轮子，而项目 utils 目录下原本就有的？

请逐条列出清单。注意：只回答分析，先不要擅自动手修改代码！
```

::: warning 为什么一定要加“只回答分析，先不要修改”？
大模型一旦被要求“找冗余并修改”，它的极端性格会导致它一口气删掉大半个文件，甚至连核心业务逻辑也顺手剔除。  
让它先出清单，**由你这位管理者来拍板**到底删哪些，然后再让它执行精准剔除。
:::

---

### 第三斧：规则固化（把教训沉淀进 AGENTS.md）

说过一次的红线，绝不该在下一次会话里重复交代。把踩过坑的原则直接写进根目录的 `AGENTS.md` 中：

```markdown
## 架构与编码规范（防过度设计禁区）
- 优先复用项目现有依赖：写新函数前，必须先在 `/src/lib` 目录下全局检索是否有同类工具。
- 不为单一实现引入接口抽象：只有当同一业务逻辑存在两种以上实质实现时，才允许抽象 interface。
- 单文件行数红线：单个组件或工具文件超过 300 行必须停手并说明拆分理由。
```

一旦固化进配置文件，模型每一次开机会话都会自动加载这道“紧箍咒”。

## 真实翻车案例：一个上传按钮引发的血案

::: danger 翻车案例：为了一个上传，重构了整套架构
**现场**：开发者要求给个人中心加一个头像上传。AI 产出了 `AvatarUploadService`、`OssAvatarUploader`、`LocalStorageUploader`、`UploaderFactory` 和 3 个独立配置文件。  
**后果**：开发者只是本地开发，并没有申请 OSS 密钥。AI 写的工厂类默认根据环境变量路由到 OSS，结果本地启动一直报 `OSS_ACCESS_KEY_ID is undefined` 导致页面白屏。  
**诊断**：第二系统效应的经典反噬——为莫须有的“以后可能要传阿里云 OSS”提前造了一整座核电站，而当前只需要一根蜡烛。  
**解法**：果断执行第二斧事后减法：“删掉所有 OSS、工厂与事件订阅代码，改用原生的 fetch 发送 FormData 到当前后端 /api/avatar 接口”。代码量从 420 行瞬间缩减至 18 行，且开箱即跑！
:::
