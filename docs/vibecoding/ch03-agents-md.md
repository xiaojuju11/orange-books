# 第 3 章 AGENTS.md：开机必读的那一份

> 它是投入产出比最高的一份文件，因为它影响你和模型的**每一次**交互，而不是某一次。

## 为什么需要它

模型每次启动都是失忆的。

它不记得你的项目用什么包管理器，不记得测试命令是 `pnpm test` 还是 `npm run test:unit`，不记得 `prisma/` 下的迁移文件不能手改。这些事你每次都要说一遍，说了三十遍之后开始烦，然后干脆不说了——于是它第三次把测试命令写错。

项目级的知识需要工程化的管理手段，这就是 `AGENTS.md` 存在的理由：**把每次都要重复说的话，写在一个每次都会被读到的地方。**

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| AGENTS.md | 模型开工前必须读的项目说明书 | 新同事的入职手册 |
| 渐进式披露 | 主文件只说"去哪找"，细节放在被指向的文件里 | 目录页不写正文 |
| 上下文腐烂 | 文件里的信息过期了，但没人更新 | 三年前的通讯录 |

## 陷阱一：越写越厚

新手的第一反应是：把所有规矩都写进去，写两百条。

这会在两个地方崩掉。

**注意力稀释。** 前沿模型能稳定遵守的指令数量大约在 150～200 条这个量级。超过之后不是"多遵守几条"，而是**整体遵守质量下降**——后面的规则会挤掉前面规则的注意力。你写了 300 条，实际生效的可能只有前 120 条，而你不知道是哪 120 条。

**上下文腐烂。** 代码天天在变，架构在演进，那份文件不动。三个月后它描述的是一个已经不存在的项目，而模型还在认真遵守它。

## 解法：目录式，而不是百科式

既然问题不是"信息不够"而是"信息什么时候被读到"，那就改成按需加载：

```text
AGENTS.md（控制在 100 行左右）
├─ 项目是什么 + 技术栈
├─ 常用命令（装依赖 / 跑测试 / 构建）
├─ 目录职责
└─ 一句话指路：
     "改认证相关，先读 docs/auth.md"
     "改数据库相关，先读 docs/db.md"
```

主文件负责**指路**，真正的知识放在 `docs/` 里。模型只在需要时读那一份，上下文干净，更新也简单——改认证规范只动 `docs/auth.md`，不用碰主文件。

## 三个层级

`AGENTS.md` 不是一份文件，是一套层级系统，作用范围不同：

| 位置 | 范围 | 放什么 | 要不要提交 |
| --- | --- | --- | --- |
| `~/.codex/AGENTS.md` | 全局，所有项目 | 个人偏好，比如"用中文回复""别写总结段" | 不提交 |
| 项目根目录 | 当前项目 | 技术栈、命令、约定，团队共享 | 提交 |
| 子目录 | 该目录 | 前端一套、后端一套，各自约定 | 提交 |

分层的意义：个人偏好不该污染团队仓库，团队约定也不该跟着你换项目。

## 写什么：三个维度

一份好的主文件回答三个问题，顺序别乱：

**WHAT——这是什么。** 一句话说清项目定位，加上技术栈和目录结构。这一段决定了模型后面所有判断的坐标系。

**WHY——为什么这么设计。** 每个模块的职责，以及当初为什么选这个方案。这一段最容易被省掉，也最能减少返工：模型不知道"为什么不直接用 ORM"，就会热心地给你换成 ORM。

**HOW——具体怎么做。** 测试怎么跑、怎么构建、用哪个包管理器、改完必须跑什么检查。

## 一份可以照着改的模板

```markdown
# 项目名：一句话说清这是什么

Next.js 14，App Router + TypeScript。

## 常用命令
- `pnpm dev`：启动开发服务器
- `pnpm test <file>`：只跑单个测试文件，不要跑全量
- `pnpm typecheck`：改完代码必须跑一次

## 目录职责
- `/app`：页面和路由
- `/lib`：跨模块共享的工具函数，写之前先搜一遍，别重复造
- `/prisma`：数据库 schema，迁移文件不要手改

## 重要约定
- 推送用 `--force-with-lease`，不要用 `--force`
- 环境变量在 `.env.local`，不要提交
- 动认证之前，先读 `docs/auth-patterns.md`
```

注意最后一条的写法：**指路，不解释**。它没有把认证规范抄进来，只说了去哪儿看。

## 把它当活文件养护

两件事，缺一不可：

**当错题本用。** 每次翻车之后，把"这次错在哪"补进去。不是补一句"要注意边界情况"，是补一句具体的："`calculateTotal` 里金额单位是分不是元，别当元处理"。具体的教训才会被遵守，抽象的提醒会被忽略。

**定期做减法。** 每隔几周让模型自己审一遍这份文件：哪些规则已经过期？哪些和代码对不上？哪些两条其实是一条？删掉的规则比加上的规则更值钱。

## 翻车现场

::: warning 写了 300 条，等于一条都没写
某次排查一个反复出现的错误，翻 `AGENTS.md` 才发现：第 8 条就写着"不要用 `any`"，但模型一直在用。

不是它没读，是 300 条里第 8 条分到的注意力太少了。删到 80 条之后，同一个问题不再出现。
:::

## 自测三问

1. 你现在有 `AGENTS.md` 吗？如果有，它有多少行？超过 150 行的部分分别属于哪一类信息？
2. 你的项目里有哪些知识适合"指路"而不是"内联"？举两个例子。
3. 为什么"定期删规则"比"持续加规则"更重要？
