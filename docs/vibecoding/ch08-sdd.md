# 第 8 章 SDD：把决策和规划分开

> 规格驱动开发救不了"你根本没想清楚"这件事。它的价值在于逼你把想法写下来，而不是替你产生想法。

## 为什么需要它

一句话需求进去，三千行代码出来，方向全错——这类事故的根源不在执行，在**决策和执行被混在一起做了**。

传统做法是一边想一边写：边画图纸边砌墙。AI 时代这个错误被放大了，因为它砌墙太快，你来不及发现图纸是错的。

SDD（Spec-Driven Development，规格驱动开发）把这个过程拆成两步：

- **spec 回答"做什么"**——要什么功能、什么行为、什么边界；
- **plan 回答"怎么做"**——拆成哪些任务、按什么顺序、动哪些文件。

先有 spec，再从 spec 里提取 plan，最后让模型按 plan 干活。

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| spec | 对"做成什么样"的书面描述 | 建筑图纸 |
| plan | 从图纸拆出来的施工任务清单 | 施工工序表 |
| Plan Mode | 让模型先出计划、不动手的模式 | 先开会再开工 |

## 两种典型用错的方式

**甩手掌柜型。** 丢一句"帮我写个 spec"，然后拿着它生成的规格直接开工。

这是最危险的一种。**在信息不充分的情况下让它生成 spec，等于让它把关键决策全做了**——选哪张表、字段怎么加、状态怎么流转，全在 spec 里定死了。等你三天后发现表结构选错，改起来就是重建。

**劳模型。** 把 plan 写到最细的每一步，模型只负责打字。

这等于放弃了 SDD 的全部收益，还多花了一倍时间写文档。plan 的价值是"对齐"，不是"代劳"。

## 解药：先讨论，再出计划

正确的顺序是三段，中间那段最容易被跳过：

### 一、先摸底

```text
先别出方案。把和"订单退款"相关的代码读一遍，然后告诉我：
1. 现在退款是怎么实现的？走哪个入口、写哪张表？
2. 如果要支持"部分退款"，会牵扯到哪些地方？
3. 有哪些地方我可能没意识到会被影响？
```

目的是让它把**你不知道自己不知道**的部分摊开。

### 二、让它抬杠

```text
我倾向于在 orders 表上加 refunded_amount 字段来实现部分退款。
你觉得有什么问题？有没有我没考虑到的方案？
不要顺着我说，先说毛病。
```

最后一句必须有。不加这句，你得到的是"这个方案很好，建议补充……"。

加了之后，你可能会听到："加字段之后，历史订单的默认值怎么定？如果一笔订单多次部分退款，单字段存不下累计值。"——这类问题如果到写代码时才发现，返工成本是十倍。

### 三、确认完再生成计划

```text
上面确定的决策是：
- 用独立的 refunds 表，不用在 orders 上加字段
- 一次退款一条记录，支持多次部分退款
- 不支持跨订单合并退款

基于这些，生成一个 plan：拆成任务，标出每个任务动哪些文件、依赖哪个任务、
怎么验证。
```

注意：**决策是你给的，它只负责拆。** 这一句之差，决定了 plan 是在落实你的判断，还是在落实它自己的判断。

## 适用边界

SDD 最适合**批量开发同类型的项目**：一整套管理后台、一批相似的活动页、一组同构的接口。因为 spec 和 plan 可以复用，第二次开始成本很低。

一次性小脚本、半天就扔的东西，写 spec 的时间比写代码长，不值得。

## 翻车现场

::: warning 三天后才发现表结构错了
需求是"用户可以收藏商品"。

一句"帮我写个 spec"，产出很漂亮：`favorites` 表，`user_id` + `product_id` + 时间戳。

三天后运营提要求："收藏要能分组。" 这时才发现，一个字段的差别——`user_id + product_id` 唯一，还是 `user_id + group_id + product_id` 唯一——决定了整张表要不要重建。

这个问题，在"先摸底 + 抬杠"那一步，问一句"以后会不会需要分组"就能提前暴露。
:::

## 自测三问

1. 你上一次让 AI 写计划，是"它拆你确认"，还是"它连方案一起定了"？
2. "先别出方案，先读代码"这句话，能避免哪一类返工？
3. 什么样的任务不值得写 spec？举一个你自己的例子。
