# 第 6 章 机器能拦的，别用人眼

> 凡是能被机器感知并自动拦截的错误，都不该消耗你的注意力。

## 为什么需要它

AI 写功能老出 bug，本质上是两个缺口：

1. 产出的时候**没有人踩刹车**——它不知道什么时候该停；
2. 产出之后**没有东西自动验收**——你只能一行行看。

第一个缺口上一章用"减法"补了一半。第二个缺口，靠人眼是补不完的：一段 300 行的改动，认真看要 20 分钟，而它 3 分钟就写完了。你的眼睛永远追不上它的手。

所以验收必须换一种做法：**把它变成机器跑一遍就能给结论的东西。**

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| 闸门 | 必须通过才能往下走的检查点 | 机场安检 |
| hooks | 在特定时机自动触发的脚本 | 门一关就自动上锁 |
| 质检清单 | 团队对"合格"的书面定义 | 出厂检验单 |

## 四道闸门

按成本从低到高排，每一道都要有明确命令：

| 闸门 | 抓什么 | 例子 |
| --- | --- | --- |
| 类型检查 | 结构层面的错，改签名忘了改调用方 | `pnpm typecheck` |
| 代码规范 | 风格与常见陷阱，未使用变量、隐式 any | `pnpm lint` |
| 单元测试 | 行为层面的错，逻辑写反了 | `pnpm test` |
| 构建 | 打包层面的错，循环依赖、环境变量缺失 | `pnpm build` |

关键不在有这四样，在于**它们是不是一句话就能跑**。如果跑一次测试要先起三个服务、改两个配置，那它就不会被跑——也就等于不存在。

## 让闸门必然发生

检查存在，但你忘了跑，等于没有。

`hooks` 的作用就是让它不依赖人的记性：

- 每次编辑文件后自动跑一次 lint（只针对这个文件，别全量）；
- 每次提交前跑一次 typecheck；
- 每次推送前跑单测。

原则：**能在无人操作的情况下发生的检查，就不要设计成需要人记得去点一下。**

## 质检清单：先定义什么叫合格

机器能判对错，但判不了"这算不算糊弄"。那部分要写成人能读的条目，放进 `AGENTS.md`：

```markdown
## 代码质检标准
- 单个模块不超过 500 行，超了必须拆
- 图标一律用项目 icon 组件，不要用 emoji 顶
- 新增工具函数前先搜现有代码，禁止重复实现
- 禁止吞错误的空 catch，要么处理要么往上抛
- 新增接口必须有参数校验和错误处理
- 涉及用户输入渲染的地方，必须考虑 XSS
```

这些条目的共同点：**可以被逐条对照**。"代码要优雅"没法对照，"不超过 500 行"可以。

## 翻车现场

::: warning 改了"顺手"的一行
改上传组件时，顺手把 `formatBytes` 的返回值从字符串改成了数字，觉得"这样更清晰"。

单测没覆盖这个函数，`pnpm build` 能过，因为类型是 `any`。

上线后文件大小显示成 `1024` 而不是 `1 KB`。查了两个小时。
:::

事后复盘，问题不在那一行改动，在于：**类型检查没开严格模式，单测没覆盖工具函数，而这个改动看起来太小，不值得跑一遍全量测试。**

三个缺口同时存在，才让一行改动跑到了线上。

## 一个反直觉的结论

闸门越多，你**越敢**让 AI 改代码。

没有闸门的时候，它动什么你都紧张，因为唯一的验收方式是你逐行读。有了闸门，你可以放心让它一次改 20 个文件——只要绿灯全亮，风险就被压在一个可接受的范围内。

**安全感不是来自代码写得完美，是来自错误跑不掉。**

## 自测三问

1. 你的项目现在有哪几道闸门？分别一条命令能跑完吗？
2. 有没有哪个检查"存在但从来没人跑"？为什么？
3. 你的"合格"是写下来的，还是在你脑子里？写下和不写下的区别是什么？
