# 第 6 章 机器能拦的，别用人眼

> 从“提示词工程师”蜕变为“流水线架构师”：凡是能被机器自动感知并拦截的错误，永远不该消耗人类的注意力。

## 为什么需要它

AI 写功能总是小错不断、偶发翻车，根本原因在于两个不可忽视的工程缺口：

1. **产出时缺乏实时刹车**：它不知道什么时候该收手，容易过度设计和随意发挥；
2. **产出后缺乏自动化验收**：全靠人类逐行肉眼 Review。

一段 300 行的代码改动，人类工程师逐行审查、核对上下文至少需要 15～20 分钟；而 AI 重新生成它只需要 30 秒。**你的眼睛永远追不上它的手速。** 如果把精力消耗在找拼写错误、查未定义变量、对接口签名这种低级体力活上，你很快就会沦为疲惫不堪的人肉质检员。

因此，Vibe Coding 工程师必须树立一个最顶层的质量原则：

> **“凡是能被机器自动感知并拦截的错误，永远不该消耗人类哪怕一秒钟的注意力。”**

必须建立一套由机器自主拦截、自主报警、甚至自主修复的**自动化验证流水线**。

---

## 核心认知突破：硬约束（Hooks）优于软约束（提示词）

许多初学者最常犯的错误，就是试图把所有的代码检查规则全部写进提示词或 `agent.md` 里：“改完代码请记得跑一下 lint”、“不要引入未使用的变量”。

**这在工程上被称为“软约束”。**

软约束的致命问题在于：**它受制于大模型的概率本质与注意力稀释。**  
随着对话轮次增加，上下文中塞满代码，模型有约 **5% 的概率**会选择性忽略掉你的文字叮嘱。在工业级项目中，5% 的漏检率就意味着线上故障。

相比之下，配置在 Agent 底层的 **Hooks（钩子机制）** 属于**“硬约束”**：
- 它不在自然语言对话里跟 AI 讨价还价；
- 而是由开发工具在系统底层（例如 `post_tool_use`，即每次编辑文件后）强制触发脚本；
- 一旦检查不通过，脚本直接以 `exit 2` 阻断流程，并将机器报错信息原汁原味回传给模型让其立刻就地自愈。
- **执行率是绝对的 100%！**

## 术语表（人话翻译）

| 术语 | 人话白话 | 生活类比 |
| :--- | :--- | :--- |
| **流水线架构师 (Pipeline Architect)** | 不再纠结打字措辞，转而搭建自动化检查与拦截机制的工程师 | 工厂里不亲自包装螺丝，专门设计全自动质检传送带的总工 |
| **软约束 (Soft Constraint)** | 写在文本里的建议与规范，模型可能因注意力稀释而漏执行 | 墙上贴的“请自觉轻声关门”提示牌 |
| **硬约束 (Hard Constraint / Hooks)** | 由系统底层触发的拦截脚本，执行率 100%，不达标直接熔断 | 门上安装的液压防撞阻尼锁，门一推必定自动缓冲合紧 |
| **质检标准清单 (Checklist)** | 对“合格代码”设立的明确可机检或可对齐指标 | 出厂产品必须满足的 10 项物理检验公差表 |

## 链路一览：机器自闭环质检流程

```
AI 触发代码编辑 (tool_use)
          │
          ▼
底层 Hooks 自动拦截 (post_tool_use) ──► 自动执行增量脚本 (lint_changed.sh)
          │
     ┌────┴───────────────────────────┐
     │                                │
 (通过 / Exit 0)               (失败 / Exit 2 阻断)
     ▼                                ▼
推进至四道闸门流水线            错误堆栈直接甩回上下文，强制 AI 就地修复 (0人肉介入)
  ├─ 1. Type Check (类型检查)
  ├─ 2. Lint (静态代码规范)
  ├─ 3. Unit Test (核心单测)
  └─ 4. Build (全量构建)
     │
     ▼
【代码级 100% 绿灯安全放行】 ──►（注意：仍存视觉盲区！）
```

## 落地实操：四道自动化闸门

一套完整的机器自检流水线由四道关卡组成，按执行成本从低到高排列。每一道都必须能够**通过单行命令极速执行**：

| 闸门 | 核心抓取的问题 | 触发时机 | 执行命令示例 |
| :--- | :--- | :--- | :--- |
| **1. 类型检查 (Type Check)** | 参数签名改动未同步、类型不匹配、隐式 any | 每次保存 / 提交前 | `pnpm typecheck` |
| **2. 代码规范 (Lint)** | 语法规范、未使用变量、未处理的 promise、防抖缺失 | 编辑工具调用后 (`post_tool_use`) | `pnpm lint:staged` |
| **3. 单元测试 (Unit Test)** | 业务逻辑写反、极端边界数据崩溃、计算公式错误 | 提交前 (`pre-commit`) | `pnpm test:changed` |
| **4. 生产构建 (Build)** | 循环依赖、动态导入路径错误、环境变量未配置 | 推送前 (`pre-push`) | `pnpm build` |

::: tip 极速执行是生命线
如果跑一次测试需要先手动起三个 Docker 容器、配置两个数据库，AI 就根本无法高效自测。**闸门必须做到开箱秒跑（最好只检测当前变动文件）**，才能让机器真正闭环转动起来。
:::

## 建立契约：质检标准清单（Checklist）

自动化工具只是执行者，必须配合标准化的**质检清单（Checklist）**才能明确“什么叫合格”。

在项目 `docs/acceptance_criteria.md` 中固化以下硬指标，要求 AI 自检或在 Review 层逐条扫描：

```markdown
# 代码合格通用质检清单（Checklist）

1. [模块体量] 单文件代码行数严格控制在 500 行以内，超过必须合理拆分组件或抽离 hook。
2. [异常处理] 严禁出现吞没错误的空 catch！要么妥善处理并记日志，要么明确向上抛出。
3. [交互安全] 涉及用户输入渲染的地方，必须使用安全防护组件过滤 XSS 与 SQL 注入漏洞。
4. [高频防护] 所有提交、保存、点赞等触发写操作的按钮，必须强制添加防抖（Debounce）处理。
5. [依赖整洁] 严禁重复实现项目现有工具函数；图标一律使用项目统一的 Icon 组件，严禁使用 emoji 顶替。
```

这些指标没有任何模棱两可的形容词，每一条都能直接得出“是”或“否”的确定判断。

## 真实翻车案例：代码全绿却埋下生产雷

::: danger 翻车案例：格式化工具返回值引起的灾难
**现场**：开发者让 AI 优化上传组件，AI 顺手把工具函数 `formatFileSize()` 的返回值从字符串（`"1024 KB"`）改成了纯数字（`1024`），自认为“纯数字更方便上层做数学运算”。  
**后果**：该工具函数在项目中被 8 个列表页面共用。由于历史遗留问题，该处未开启强类型拦截，且单测只测了组件没测工具函数。`pnpm build` 顺利通过，上线后全站文件大小单位全部丢失，数万条数据展示错乱。  
**解法**：在 Hook 中配置 TypeScript `noImplicitAny` 和严格检查模式。当我故意将返回值类型改错时，提交必须在本地被当场拦死！拦不住，说明流水线就是纸糊的。
:::

## 关键预警：流水线的致命盲区

当类型检查、Lint、测试和 Build 全部亮起绿灯时，很多工程师就以为大功告成了。

**千万小心！这是最大的认知误区。**

传统的代码级流水线只能验证“逻辑对不对”、“打包成不成”，但**对 UI 视觉层面彻底失明**：
- 按钮逻辑完全正确，但被上层的 Toast 弹窗遮挡了一半；
- 表格数据渲染无误，但在窄屏手机端文字全部挤压换行重叠；
- 暗色模式下由于写死了黑色字号，导致深色背景下字变成了一片漆黑。

代码管不到的地方，必须靠视觉来解决。

## 自测三问

1. 为什么把测试规范写在提示词或 `agent.md` 里叫“软约束”？它相比 Hooks 硬约束有什么缺陷？
2. 在流水线四道闸门中，按成本和运行速度，应该优先将哪个检查配置在 AI 编辑文件的实时 Hook 中？
3. 如果代码编译通过、测试全绿、构建成功，是否意味着该功能可以 100% 放心上线？为什么？
