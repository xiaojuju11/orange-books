# 第 4 章 上下文的六个动作

> 上下文窗口不是越大越好，而是越干净越好。管理上下文，本质上就是在管理 AI 的短期记忆。

## 为什么需要它

你可能经常遇到这种让人抓狂的场景：

同一个会话聊了两个小时，改了七八个文件。在第 20 轮的时候，你明确跟它说："这次**不改数据库结构**，用现有字段兼容"。它当时答应得好好的。

结果到了第 45 轮，它突然又在代码里加了一个新字段，甚至把之前的表结构全改了。你质问它，它还理直气壮地回答："按照之前讨论的方案，需要新增这个字段。"

它撒谎了吗？**完全没有。**

"之前的方案"确实真真切切躺在它的上下文里——只不过那是你在二十轮前早就否决掉的废案。大模型没有人类那种"自然遗忘"和"主次权衡"的能力：被否决的假设、试错报错的几百行堆栈、废弃的代码片段，和当前的最终决定混在一起，权重几乎一模一样。

这就是典型的**上下文腐烂（Context Rotting）**与**注意力稀释（Attention Dilution）**：
- **信息都在，但已经不再代表当下事实。**
- 前沿大模型能稳定严格遵守的规则指令通常在 150～200 条左右。会话越长，上下文塞得越满，模型遵循指令的质量就会呈断崖式下跌，开始"前言不搭后语"、"胡乱自由发挥"。

很多初学者唯一的动作就是一直点"继续"，直到 AI 彻底变傻，最后叹口气归咎于"这模型不行"。其实，问题不在模型，而在**上下文太脏了**。

## 术语表（人话翻译）

| 术语 | 人话白话 | 生活类比 |
| :--- | :--- | :--- |
| **上下文窗口 (Context Window)** | 这一轮对话中，AI 眼前能看到的全部信息总和 | 办公桌面上能摊开的图纸面积 |
| **上下文腐烂 (Context Rotting)** | 废弃的旧假设、跑不通的报错和最新决定混杂在一起 | 桌上摊着三张作废草稿，不小心按旧草稿施工 |
| **注意力稀释 (Attention Dilution)** | 灌入的信息太多太长，模型抓不住真正重点 | 老师在黑板上写满了整整十块板书，学生不知道考哪道 |
| **交接文件 (HANDOFF.md)** | 将当前真实状态、进展与踩坑记录在独立物理文件里 | 下班交班记录卡，接班同事看一眼就能接着干 |
| **独立 Review** | 换一个干净的会话或小助手，只看输出结果，不看思考过程 | 医院里的"专家盲审"或"第三方质检抽检" |

::: info 💡 厘清三种记忆：AGENTS.md vs Context vs HANDOFF.md
很多初学者容易把它们搞混，其实它们的分工极其清晰：
1. **`AGENTS.md`（长期记忆）**：项目的入职手册，每次启动 AI 必读（技术栈、禁区、架构指路）。
2. **`Context`（短期记忆）**：AI 当前会话的眼前脑容量，干久了会脏，需要用本章的 6 个动作主动清理。
3. **`HANDOFF.md`（跨会话接力棒）**：会话要清空时的临时落盘备忘录，专供下一个新会话无缝接班。
:::

## 0基础第一步：怎么看你的上下文状态？

很多小白根本不知道当前会话塞了多少东西，总是等到它胡言乱语、报错卡死才意识到出了问题。

在主流的 AI 编程工具中，你随时可以检查上下文健康度：

- **Claude Code**：在输入框直接打 `/context`，可以实时看到当前占用的 Token 数量、占比，以及哪些文件占用了最多空间。
- **Codex / Cursor**：输入 `/status` 或查看窗口底部的状态栏与上下文指示条。

::: warning 黄金 50% 警戒线：不要等到爆满才处理
新手最容易犯的错误，就是以为上下文要到 100% 报错才算满。

**千万不要等！** 实践证明：**当上下文占用达到 50% 左右（或者连续交互超过二三十轮），模型的注意力就已经开始发散了。** 此时就该主动进行整理与交接，别等它开始翻车。
:::

::: tip 关掉 Auto-Compact（自动压缩）
很多工具默认开启了 `autocompact`（自动压缩）。强烈建议在设置中**把它关掉**！

为什么？因为工具自带的自动压缩通常在上下文快要撑爆（85%~90%）时才被动触发。这时候上下文里早就堆满了试错的垃圾代码和报错信息。此时自动压缩，**等于把一堆垃圾总结成浓缩垃圾**喂给接下来的模型。正确的姿势是**由你主动掌控时机、手动定向清理**。
:::

## 动作详解：小白也能精准打出的 6 张牌

### 动作 1：`/continue`（继续）—— 绿灯顺畅时的一鼓作气

- **做什么**：直接在当前基础上继续下一轮对话，保留所有历史记录，不做任何清理。
- **什么时候用**：
  - 任务目标单一明确，且上下文在 50% 安全线内。
  - 前面几步全部跑通，没有走弯路，方向完全正确。
  - 比如刚做完"创建按钮组件"，紧接着让它"为按钮添加点击事件"。
- **0 基础避坑**：
  千万别把 `/continue` 当成早九晚五的唯一点读机！一旦遇到连续两次报错，马上停下，不要再继续了。

---

### 动作 2：`/rewind`（回滚）—— 时光倒流的单机读档

- **做什么**：类似单机游戏里的"回到上一个存档点"。从某一轮重新开始，把那一轮之后所有走歪的对话、报错全部清理出上下文。
- **什么时候用**：
  - 你让它修一个 bug，第 1 轮没修对，第 2 轮它开始改底层配置，第 3 轮直接把项目搞崩溃了。
  - 这个时候在烂摊子上接着糊泥巴只会越陷越深。果断打 `/rewind`，退回到它动手改之前的干净节点！
- **实战铁律**：
  > **改到第三轮还不对，立刻停下回滚！**  
  > 绝对不要在已经走偏的泥潭里接着调试。退回到分叉口，换一个清晰的提示词重新切入。

---

### 动作 3：`/compact`（定向压缩）—— 保留精华的精准大扫除

- **做什么**：丢弃过程中的代码尝试和啰嗦讨论，只保留最终共识与待办事项。
- **高阶技巧：给压缩一个明确的方向**  
  如果你只输入孤零零的一句 `/compact`，模型只能靠概率猜你想留什么。正确的姿势是**给它具体的指令**：

```text
/compact 压缩当前上下文，请严格保留：
1. 已经敲定的架构方案（例如：JWT 放在 header 中，不走 cookie）
2. 尚未完成的待办任务清单
3. 已经排查并证伪的坑（例如：千万不能修改 auth/session.ts 中的 Redis Key 命名规范）
不要保留：中间尝试失败的代码片段、讨论过程中的各种反问。
```

---

### 动作 4：`/clear`（清空重开）+ `HANDOFF.md` —— 投入产出比最高的换班神器

- **做什么**：彻底抹掉当前会话，开启一张 100% 洁白无暇的新答卷。
- **什么时候用**：
  - 上一个大功能做完了，准备开始做另一个不相关的功能（例如：登录做完了，准备做支付）。
  - 会话太长（达到 50% 警戒线），或者感觉模型开始迟钝。

#### 核心打法：压缩前先落盘到 `HANDOFF.md`

直接 `/clear` 会让 AI 彻底失忆。最科学的姿势是让它**先把大脑里的有效资产写入一个叫 `HANDOFF.md` 的交接文件**，然后再清空：

::: tip 标准交接三部曲
1. **落盘指令**：在清空前，对 AI 说：
   ```text
   把当前的进展、待办事项、已知的坑写进根目录的 HANDOFF.md 文件。
   要求：具体到哪怕明天换一个全新的会话，只读这个文件就能直接继续开工，不需要问我任何问题。
   ```
2. **清空会话**：输入 `/clear`。
3. **无缝接棒**：在新会话的第一行直接发送：
   ```text
   读一下根目录的 HANDOFF.md 文件，我们要继续推进下一步。
   ```
:::

#### 一份标准的 `HANDOFF.md` 长什么样？

```markdown
# 认证重构 - 交接文档

## 已完成
- JWT 签发逻辑迁移到 auth/jwt.service.ts
- 登录接口已切到新逻辑，单元测试已跑通通过

## 待办
- refresh token 还没迁移，旧逻辑在 auth/legacy.ts:120
- bar.ts 有个 unused import 的 warning，顺手修掉

## 已知的坑（证伪的路径）
- 别动 auth/session.ts 的 Redis key 格式，线上有老版本持久化数据依赖
- 方案 A（在中间件里验签）已经尝试过，行不通：中间件拿不到全局 user context
```

::: danger 为什么"已知的坑"这一栏最值钱？
因为 AI 新开会话后是失忆的。它知道目标是"做验签"，但如果不告诉它"方案 A 行不通"，**它一定会兴高采烈地把之前走错的死路再走一遍**！记录已经证伪的路径，能省下几十分钟的无谓试错。
:::

---

### 动作 5：`/branch`（分支任务）—— 开启平行宇宙去探路

- **做什么**：基于当前会话的上下文，分叉出一个平行的独立会话。
- **什么时候用**：
  1. **需求调研与竞品分析**：在规划新需求时，想让 AI 去 GitHub 上搜索高星类似项目，分析别人为什么这么设计、做了哪些取舍。这种全网搜索会产生大量网页文字，直接在主会话做会严重污染上下文。用 `/branch` 开一个分支去调研，整理出结论后，再把精华带回主线。
  2. **方案对比 A/B 测试**：主线代码写得好好的，突然想试试能不能用新技术重构某一部分。在分支里放手去试，试成功了把代码搬回来；试失败了直接关掉分支，主线完好无损。

---

### 动作 6：`subagent`（子代理 / 子会话）—— 派小弟独立办事

- **做什么**：在主会话内部生成一个子代理（Subagent）。子代理拥有**独立洁净的上下文小房间**，它在自己的小房间里看几十个文件、跑分析，最后只把精炼后的最终结果汇报给主会话。
- **什么时候用**：
  1. **海量资料检索**：需要翻看全项目 50 个文件寻找某一个函数的用法，派 subagent 去翻，别把翻找的过程堆进主会话。
  2. **收尾的独立 Review（终极质检关卡）**：
     - 如果在同一个会话里问它："你刚才写的代码没问题吧？" 它一定会顺着自己的思路回答："逻辑严密，没有任何问题。"（自我确认偏误）。
     - 正确做法：开一个干净的 subagent，只把 `git diff`（改动代码）递给它："假设你是一名严苛的质检员，找出这段代码里的安全漏洞和隐患。"
  3. **双模型机制与审查 Skill**：
     - 用一个模型生产（比如 Claude），审查时派 subagent 调用另一个模型（比如 DeepSeek 或 GPT）。不同模型的训练集不同，互相挑毛病命中率极高！
     - 结合专业审查技能库，例如三元开源的 [sanyuan-skills (GitHub)](https://github.com/sanyuan0704/sanyuan-skills)，利用预设的审查清单（Checklist）逐条扫描代码规范、空 catch、边界异常与 XSS 隐患。

## 0基础选择决策树：面对 AI，这一轮我该按哪张牌？

面对屏幕上的 AI，不知道该用哪个动作？对照下面这张决策表一秒判断：

| 你的当前状态 | 推荐动作 | 应该打出的指令 / 提示词 |
| :--- | :---: | :--- |
| 代码跑通，逻辑清楚，正一鼓作气做同个小功能 | <span class="badge-action">/continue</span> | "很好，继续实现下一个函数..." |
| 修 bug 试了两次越来越乱，改了不该改的代码 | <span class="badge-action">/rewind</span> | 回滚到动手前的干净轮次，重新换清晰指令 |
| 同一个功能干了很久，上下文到了 50% 警戒线 | <span class="badge-action">/compact</span> | 定向输入：保留方案、待办和踩坑记录，剔除试错细节 |
| 当前模块开发完毕，准备开始写下一个全新模块 | <span class="badge-action">/clear</span> | 先让它写 `HANDOFF.md`，然后清空，新会话读取接着干 |
| 想在当前进度上尝试一个激进的备选架构方案 | <span class="badge-action">/branch</span> | 开启平行分支探索，成了合代码，败了直接关 |
| 需要扫遍几十个文件查资料，或者收尾做代码质检 | <span class="badge-action">subagent</span> | 派独立小弟看 `git diff`，参考 [sanyuan-skills](https://github.com/sanyuan0704/sanyuan-skills) 标准挑刺 |

## 翻车现场（血泪实录）

::: warning 翻车案例一：一个会话干完四件事
**现场**：上午在一个会话里改登录、改缓存、修样式，一顺百顺。下午在同一个会话里做第四件事——权限重构，AI 突然开始发疯：把早上已经删掉的废弃接口又偷偷调了回来。  
**根因**：前三个任务的代码片段全部赖在上下文里，模型在长窗口下分不清哪个是"现在的写法"，哪个是"淘汰的旧写法"。  
**解法**：做完一件事，就该换个会话；换任务不换会话，必然反噬。
:::

::: danger 翻车案例二：在泥潭里死磕六轮
**现场**：一个小报错，AI 第一轮改了 A 文件，报错没消；第二轮改了 B 文件的配置，报了新错；到了第六轮，半个项目的配置文件都被它改得面目全非。  
**根因**：上下文里堆满了整整五轮失败尝试的报错日志。它已经被带偏到了九霄云外。  
**解法**：牢记**改到第三轮还不对，立刻停下并 `/rewind` 回滚**，绝不给它在烂泥地上接着糊的机会！
:::

## 老司机经验规则（心法口诀）

1. **换任务就换会话**：不相关的需求千万别塞在一个会话里，各回各家。
2. **50% 警戒线主动干预**：一个任务交互二三十轮，就主动压缩或交接，别等机器卡顿或胡言乱语。
3. **改到第三轮不对立刻回滚**：别在烂摊子上接着糊，回滚重开成本最低。
4. **交接前必落盘**：用 `HANDOFF.md` 记录证伪的坑，这是防止失忆模型重复踩雷的唯一护身符。
5. **复杂检索与质检放隔壁**：能让 `subagent` 在独立房间解决的脏活累活，绝不带回主桌面污染主干。

## 自测三问

1. 你平时的默认动作是不是只有"继续"？回想一下，上一次 AI 突然犯糊涂，是不是因为会话拖了太长？
2. 为什么说关掉工具的 `autocompact`（自动压缩），改用手动定向压缩，产出质量会高得多？
3. 如果 `HANDOFF.md` 里只能保留一个段落，你选哪一段？为什么"已知的坑"比"已完成的功能"更重要？
