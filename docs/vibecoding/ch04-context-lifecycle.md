# 第 4 章 上下文的六个动作

> 上下文不是越大越好，是越干净越好。

## 为什么需要它

同一个会话跑两个小时，会出这种事：

第 20 轮你决定"这次不改数据库"，第 45 轮它又给你加了一个字段，还理直气壮地说"按之前的方案需要这个字段"。

它没说谎。**"之前的方案"确实在它的上下文里**——只不过是你二十轮前就否掉的那个。上下文不会自己过期，被否掉的假设和当前的决定躺在一起，权重还差不多。

这就是上下文腐烂：信息还在，但已经不代表现在的事实。

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| 上下文窗口 | 这次会话它能看到的全部内容 | 桌面能摊开的纸 |
| 上下文腐烂 | 旧假设混在当前决定里 | 桌上还摊着作废的图纸 |
| 交接文件 | 把状态写进文件，供下一轮读 | 交班记录 |

## 六个动作

一轮工作做完，你有六个选择。先记住它们解决的是不同问题：

| 动作 | 做什么 | 什么时候用 |
| --- | --- | --- |
| 继续 | 原地接着干，不清任何东西 | 任务还没完、方向确定、上下文仍准确 |
| 回滚 | 退到某一轮重新开始，清掉之后的 | 最近几步走歪了，但前面的判断还有效 |
| 压缩 | 保留要点，丢掉过程细节 | 会话变长但任务还要继续 |
| 清空 | 全新会话，什么都不带 | 换一个不相关的任务 |
| 分支 | 带着当前上下文去开一个新任务 | 主线正确，但要试一条岔路 |
| 子代理 | 独立上下文，只把结果带回来 | 一件事可以整个外包出去 |

大部分人的默认动作只有一个：**继续**。然后在一个越来越脏的会话里，越干越乱，最后归因为"模型不太行"。

## 最有用的是压缩

六个动作里，压缩的收益最高，也最容易被用错。

**第一，手动压，不要等自动。** 自动压缩通常发生在快满的时候，那时上下文已经脏了很久，压出来的是脏东西的摘要。

**第二，压缩要给方向。** 一句"压缩一下"它只能按重要性自己猜。给方向才准：

```text
压缩上下文，保留：
- 已经确定的方案（JWT 放 header，不放 cookie）
- 还没做完的三件事
- 踩过的坑（Redis key 格式不能改）
不要保留：中间试错的几版代码、被否掉的方案
```

**第三，压缩前先落盘。** 这是最有价值的一条：在压之前，让它把状态写进一个文件。

```text
把当前的进展、待办、已知的坑写进 HANDOFF.md。
要求：我明天开一个全新的会话，只读这个文件就能继续工作，不用问你任何问题。
```

写完 `HANDOFF.md`，你就可以放心 `/clear`，新会话第一句是"读一下 HANDOFF.md，我要继续"。断开上下文和不断开，效果一样。

## HANDOFF.md 长什么样

关键是**具体到能直接开工**，不是写周报：

```markdown
# 认证重构 - 交接

## 已完成
- JWT 签发逻辑迁移到 auth/jwt.service.ts
- 登录接口已切到新逻辑，测试通过

## 待办
- refresh token 还没迁移，逻辑在 auth/legacy.ts:120
- bar.ts 有个 unused import 的 warning，顺手修

## 已知的坑
- 别动 auth/session.ts 的 Redis key 格式，线上有老数据依赖
- 方案 A（中间件里验签）试过，不行：中间件拿不到 user context
```

"已知的坑"这一段最值钱。它记录的是一条**已经证伪的路径**——没有它，新会话里的模型会兴高采烈地再走一遍。

## 翻车现场

::: warning 一个会话干完四件事
上午在一个会话里改登录、改缓存、修样式，都很顺。下午第四件事——改权限——它开始胡来：把已经废弃的旧接口又调回来。

原因很简单：前三个任务的上下文全在，里面有一堆"旧的怎么写"的代码片段。它分不清哪个是"现在的写法"。
:::

## 一条经验规则

- **换任务就换会话**。不相关的事不要挤在一个会话里。
- **一个任务超过二三十轮，就该压缩或交接**。别等到它开始记错。
- **要开岔路就用分支或子代理**，别把主线的会话搞乱。

## 自测三问

1. 你现在的默认动作是哪个？有没有一种情况，你其实该清空，却一直"继续"下去了？
2. 为什么"压缩前先写交接文件"比"直接压缩"更可靠？
3. `HANDOFF.md` 里如果只能留一段，留哪段？为什么？
