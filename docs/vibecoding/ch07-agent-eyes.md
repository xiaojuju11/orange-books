# 第 7 章 给 Agent 一双眼睛

> 测试全绿不代表页面能看；代码层查不出的视觉重叠与样式坍塌，必须让 Agent 自己打开浏览器亲眼看。

## 为什么需要它

在前端 Web 开发中，你一定经历过这种荒诞的场景：

单元测试全绿、TypeScript 编译通过、Webpack 构建无告警，甚至 E2E 测试脚本也显示表单提交成功。然而当你怀着轻松的心情打开浏览器页面一瞅：
- 错误提示框由于定位计算错误，死死盖住了底下的提交按钮；
- 弹窗被父容器的 `overflow: hidden` 截掉了一半，用户根本点不到关闭图标；
- 移动端窄屏模式下，表格列宽超出屏幕，右侧操作栏被挤出视口；
- 切换到深色模式，文本颜色由于写死了灰色十六进制值，在纯黑背景下彻底隐形。

**代码没有任何语法错误，但用户眼前是一片灾难。**

这是因为传统的测试手段（Unit Test / E2E DOM 断言）断言的是“元素是否存在于 DOM 树”、“onClick 事件是否被触发”。它**根本无法断言渲染引擎在屏幕上的真实物理像素表现**！

解决视觉盲区的唯一正解：**给 Agent 补上一双眼睛 —— 让它自己打开浏览器，截图、自查、比对、闭环修复。**

---

## 核心技术路线对比：两大浏览器工具选型

很多人以为“随便接一个浏览器 MCP 插件”就行了。在真实工程中，浏览器工具分为两条截然不同的技术路线，切忌混淆：

| 维度 | 路线一：驱动型 (Driver) | 路线二：深度排查型 (Deep Debug) |
| :--- | :--- | :--- |
| **代表工具** | **`agent-browser`** / Playwright | **`Chrome DevTools MCP`** |
| **核心能力** | 模拟人类键鼠操作：打开网页、点击按钮、表单输入、全屏截图 | 读取浏览器底层运行日志：Console Log、Network 请求瀑布流、内存性能 |
| **解决的痛点** | **复现与视觉呈现**：直观发现元素重叠、样式错位、遮挡缺陷 | **定位深层根因**：页面白屏时排查哪个接口报 500、缺少什么响应头 |
| **Token 开销** | **极低（零上下文浪费）**：按需通过命令行/Skill 调度，不占预载 Token | **高**：MCP 会在开机时全量加载工具 Schema，吞噬初始上下文窗口 |
| **局限性** | 无法直接看底层网络链路的详尽 Headers | 纯文字数据诊断，**无法通过截图发现视觉层叠问题** |

::: warning 为什么强烈推荐优先选择 agent-browser 而非 MCP 方案？
很多现成的 MCP Browser 工具，会在每次新会话启动时，把巨幅的工具定义协议（Tool Definition Schema）全量注入到上下文开头，瞬间吃掉数千个 Token。  
而 **`agent-browser`** 采用延迟按需加载的 Skill / CLI 模式，调用时才产生开销，对 Chrome 与 Brave 环境适配极佳，性能和上下文开销表现远超通用 MCP！
:::

## 术语表（人话翻译）

| 术语 | 人话白话 | 生活类比 |
| :--- | :--- | :--- |
| **驱动型工具 (agent-browser)** | 能真正模拟手眼操作浏览器的智能体工具 | 一个坐在电脑前帮你狂点界面的实习测试员 |
| **深度排查型工具 (DevTools MCP)** | 专门扒开浏览器后台看接口和报错的听诊器 | 汽车修理工插在发动机上的 OBD 电脑诊断仪 |
| **视觉回归 (Visual Regression)** | 每次改动后截图，与历史标准基线做像素级对比 | 找不同游戏：对比修改前后的两张真实照片差异 |
| **Computer Use (全能系统手)** | 让模型走出浏览器，直接接管整个操作系统桌面的能力 | 秘书离开网页，直接去操作桌面文件夹和本地软件 |

## 链路一览：视觉闭环自检 SOP

```
UI 代码修改完成
      │
      ▼
调用 agent-browser 自动唤起浏览器 (打开本地开发服务器)
      │
      ├─► 1. 模拟交互：点击、输入、触发极端边界状态
      ├─► 2. 多态快照：亮色/暗色模式、宽屏桌面/窄屏手机端分别截图
      │
      ▼
Agent 自主读取截图并进行视觉质检
      │
 ┌────┴───────────────────────────┐
 │                                │
(视觉无误，排版舒展)           (发现缺陷：元素重叠 / 溢出 / 对比度失效)
 ▼                                ▼
【报告完成，允许合入】          AI 就地修改 CSS ──► 重新截图确认 ──► 达成闭环
```

## 实战上手：agent-browser 极速搭建三部曲

仅需三条命令，即可为你的本地 AI Agent 配上完整的视觉驱动能力：

#### 步骤 1：全局安装依赖
```bash
npm install -g agent-browser
```

#### 步骤 2：环境一键初始化（自动配置 Chrome / Brave 驱动环境）
```bash
agent-browser install
```

#### 步骤 3：冒烟验证
在终端中执行以下命令，观察系统是否能够自动唤起浏览器并导航：
```bash
agent-browser open baidu.com
```

## 固化到流程：在规范中立规矩

装好工具并不够，必须让“视觉自检”成为 AI 的必然反射。

在项目根目录的 `AGENTS.md` 或专用契约中，写死以下**视觉验收铁律**：

```markdown
## UI 视觉验收规范（强制执行）
凡是涉及前端界面组件（HTML/CSS/Vue/React）的新增或改动，在宣布任务完成前，必须执行以下闭环动作：
1. 启动 agent-browser 打开目标页面进行交互验证；
2. 必须截图保留证据：包含至少一张正常状态图、一张移动端（宽 375px）自适应图，以及暗色主题对比图；
3. 自查核对：确认不存在文字截断、弹窗被盖住、按钮点不动等层叠问题；
4. 只有视觉截图确认无误后，才允许向我汇报“任务已完成”并贴出截图。
```

给它这一条约束，AI 就会在交卷前自己默默打开页面、截个图、发现不对自己悄悄修好，而不是把半成品甩给你。

## 浏览器够不到的盲区：启用 Computer Use 兜底

浏览器工具只能支配网页内部的 DOM。但在实际 Web 开发中，总有一类需求会“跳出浏览器”：
- **场景**：用户点击了页面上的“导出为 Excel / PDF 报表”按钮，前端触发了浏览器系统级文件下载；
- **盲区**：页面提示“下载已完成”，但本地 Downloads 目录里的文件是否真实存在？文件大小是否为 0？下载的 Excel 里面表头字段对不对？

这类浏览器自身无法读取的操作，就要祭出终极兜底武器 —— **Computer Use（全能系统手）**：
- **原理**：Agent 直接接管操作系统桌面权限，读取本地文件系统、甚至打开系统文件查看内容；
- **工具配置**：在 Codex 中可直接在插件市场启用内置的“电脑控制（Computer Use）”；在 Claude Code 中亦可配置桌面级自动化支持。
- **定位**：它是最后的底牌。能用浏览器 API 验证的优先在浏览器里解决；涉及本地文件校验的，交由 Computer Use 闭环。

## 真实翻车案例：绿色测试背后的遮挡事故

::: danger 翻车案例：被遮盖的“支付确认”按钮
**现场**：电商结账页改版，前端单元测试覆盖率高达 95%，点击支付的 mock 请求测试完全跑通。  
**后果**：上线后半小时，客诉激增：大量用户反馈“无法完成支付”。打开真机一看：为了展示大促活动，运营团队新增了一个底部吸底的浮动 Banner。Banner 的 `z-index: 999` 恰好完全遮挡住了原本位于底部的“立即支付”按钮。在代码层面，DOM 元素安然无恙；但在视觉像素上，用户点的全是广告横幅！  
**解法**：接入 `agent-browser`。在任务指令中要求：“打开结账页，全屏截图分析支付按钮的像素坐标是否被其他层遮挡”。AI 在截图中一秒识别到重叠，自动将支付按钮的 `z-index` 调整并添加了吸底安全边距。
:::
