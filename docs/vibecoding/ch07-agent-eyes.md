# 第 7 章 给 Agent 一双眼睛

> 测试全绿不代表页面能看。代码层管不到的东西，得让它自己看。

## 为什么需要它

单元测试断言的是"这个按钮的 onClick 被调用了"，不是"这个按钮有没有被弹窗盖住"。

视觉和交互的错，天然在测试覆盖之外：布局塌了、文字溢出、Toast 挡住提交按钮、深色模式下字看不见。这些错上线后用户第一眼就发现，而你的 CI 一片绿。

解法只有一个：**让它自己打开页面看。**

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| 浏览器自动化 | 用代码驱动浏览器：打开、点、填、截图 | 一个不知疲倦的测试员 |
| 视觉回归 | 把这次截图和上一版对比，找出差异 | 装修前后拍对比照 |
| computer use | 让模型直接操作电脑桌面 | 够不到网页时的备用手段 |

## 两类工具，别混用

很多人以为"给个浏览器工具"就够了，其实要分两种能力：

| 类型 | 干什么 | 典型工具 |
| --- | --- | --- |
| 操作型 | 打开页面、点按钮、填表单、截图、读 DOM 结构 | Playwright、agent-browser |
| 排查型 | 页面不对时进去查为什么：console 报错、network 请求、性能面板 | Chrome DevTools 类工具 |

操作型负责"复现"，排查型负责"定位原因"。

只给操作型，你会得到"点完了，页面白了"这种没有信息量的结论。两个都给，它才能自己走完"复现 → 看 console → 发现接口 500 → 回头改代码"这条链。

## 怎么用

别让它"随便看看"，给它一条具体的路径：

```text
打开 http://localhost:3000/login
输入错误密码，点登录
截图，然后回答：
1. 错误提示出现了吗？在哪个位置？
2. 提示文字和输入框有遮挡或重叠吗？
3. 对比 src/design/tokens.ts 里的间距规范，这个提示的边距对吗？
如果不对，直接改，改完再截一次图给我看。
```

最后那句"改完再截一次图"是关键：它把"看"变成了闭环，而不是一份描述。

## 从"看一眼"到"每次都看"

单次截图是救火。要防回归，得把截图变成基线：

- 第一次跑，截图存成基线；
- 之后每次改动，重新截图，和基线做像素对比；
- 差异超过阈值就报出来，人去判断是"改坏了"还是"本来就要改"。

这一套做起来不复杂，但要有人先搭一次。搭好之后，UI 回归就从"靠眼睛"变成"靠命令"。

## 够不到的地方

浏览器能覆盖网页，覆盖不了桌面应用、系统弹窗、外部客户端。这种时候用 computer use 兜底——让模型直接操作鼠标键盘，看屏幕截图判断状态。

它是最后的兜底，不是首选：慢、贵、不稳定。能用 CSS 选择器定位的，别用坐标点击。

## 翻车现场

::: warning 测试全绿，按钮点不到
提交流程的单测、类型检查、构建全过。上线后用户反馈"提交按钮点不动"。

原因是新加的一个固定定位的提示条，正好压在按钮上方。DOM 里按钮还在，`onClick` 也正常，只是被盖住了。

补上截图检查之后，这类问题第一次出现就会被看见——因为图里那个按钮确实灰了一块。
:::

## 一个判断标准

问自己：**这个错误，如果我给它一张截图，它能不能自己发现？**

能，就值得接一个浏览器工具；不能（比如"这个交互手感对不对"），那还是得你自己看。

## 自测三问

1. 你的项目里，"测试全绿但页面有问题"这类 bug，最近一次是什么？如果当时有一张截图，能不能提前发现？
2. 操作型和排查型工具，你缺哪一个？
3. 视觉回归的基线由谁维护？如果没人维护，它会变成什么？
