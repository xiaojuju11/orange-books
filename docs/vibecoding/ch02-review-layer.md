# 第 2 章 幻觉消不掉，就给它包一层

> 一个有固定错误率的组件，靠"再仔细一点"救不回来，只能靠流程。

## 为什么需要它

"模型以后会不会不再胡说八道？"

这个问题问错了方向。幻觉不是模型的 bug，是**概率生成方式的固有属性**——它每一步都在猜下一个最可能的词，"猜"这件事本身没有"我确定/我不确定"的开关。你可以降低概率、增加证据、要求它引用来源，但清不零。

工程上遇到"清不零"的组件怎么办？回头看看计算机史：

- 网络会丢包，没有一条协议是靠"让链路别丢包"解决的，靠的是重传和校验；
- 磁盘会坏，没有一块盘是靠"造一个不会坏的盘"解决的，靠的是 RAID 和备份；
- 程序会写错，没有一门语言是靠"让程序员变完美"解决的，靠的是类型系统、测试、CI。

规律很一致：**不可靠的组件，都是在它外面包一层来解决的。**

模型的这一层，就是 review。

## 术语表

| 术语 | 人话 | 类比 |
| --- | --- | --- |
| 中间层 | 生产者和交付之间插进来的一道关卡 | 工厂的质检岗 |
| 独立 review | 检查者没看过生产者怎么想的，只看结果 | 盲审 |
| 上下文隔离 | 检查者开一个干净的会话 | 换个人来复核 |

## 结构长什么样

```text
你的任务
   ↓
Agent 生产（假设 90% 正确率）
   ↓
Review 中间层
   ├─ 通过 → 交付
   └─ 不通过 → 打回重做（带上具体问题）
```

这个结构的关键不在"review"三个字，在于它是**循环**。打回去不是否定，是把检查结果作为新的上下文再喂一遍——模型第二轮通常能改对，因为这次它知道了具体哪儿不对。

## "独立"才是重点

让同一个会话里的模型自查，效果接近于零。原因不是它偷懒，是**它已经看过自己的推理过程了**。

写代码时它做了十几个判断：为什么用这个数据结构、为什么跳过那个边界情况。你在同一个会话里问"有问题吗"，它会在这些判断的基础上找补理由——人类的确认偏误，模型一样有。

所以要隔离两个东西：

**隔离上下文。** 让检查者只看生产者输出的结果，不看它的思考过程。

- 开一个全新会话，把 `git diff` 作为唯一上下文，让它以检查者身份挑毛病；
- 或者让主会话派一个 subagent，子会话有独立上下文，只把结论带回主会话。

**隔离模型。** 同一个模型训练数据相同，盲区也相同。用一个模型生产、另一个模型检查，命中率会明显不同。

还有一个细节：**给它检查的标准，而不是问"你觉得有问题吗"**。后者得到的回答永远是"整体看起来不错，有几个小建议"。前者要你递一份清单过去——哪几条算不合格，逐条对照。

## 翻车现场

::: warning "看起来没问题"
同一会话里写完 200 行，你顺手问一句"这个实现有问题吗？"

它回答：整体没问题，注意一下空值处理就好。

上线三天，`null` 传进来，挂在第三个 if 里。

它没有撒谎。它只是在为刚刚写下的代码做辩护——那是它自己的产出，它天然站在生产者的立场上。
:::

## 有些事不能交给中间层

review 能兜住"写错了"，兜不住"一开始方向就不对"。这三件事必须你自己下场：

- **方案讨论**：两个技术选型到底选哪个；
- **技术选型**：引入一个新依赖，值不值；
- **看不懂的逻辑**：它写得挺顺，但你说不出为什么对。

处理方式是**苏格拉底式的提问**：不要问"这样对吗"（它会顺着你说），要问"如果并发上来会怎样""如果这条数据是空的会怎样""为什么不用另一种方案"。逼它把假设摊开。

最后养成一个习惯：**真正验收通过之前，问一句"你漏掉了什么？"**

这句话的成本是一行字，收益是偶尔捞回一个你根本没想到的情况。

## 自测三问

1. 为什么在同一个会话里让模型自查，几乎无效？有两个层面的原因，分别是什么？
2. 你现在的流程里，"打回重做"这一步存在吗？还是通过就通过、不通过就自己上手改？
3. 什么样的任务**不该**交给中间层，必须自己判断？
