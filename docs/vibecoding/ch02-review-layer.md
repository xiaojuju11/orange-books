# 第 2 章 幻觉消不掉，就给它包一层

> 承认幻觉不可消除，用“幻觉架构”增加独立 Review 中间层，把 AI 生产的可靠性从 90% 提升至 99%。

## 为什么需要它

“未来的大模型会不会彻底消除幻觉，做到 100% 正确？”

这个问题从一开始就问错了方向。

### 1. 幻觉是概率系统的固有属性

大模型的本质是 Transformer 架构，其底层机制永远是**基于前面的输入，概率预测下一个最可能的 Token**。即使给它喂进世界上最干净的训练数据，只要它是概率系统，就必然存在非零的错误率。

更要命的是，当前大模型的测评标准和对齐机制，普遍**鼓励模型给出“自信的作答”**。当它遇到不确定或没见过的场景时，它天生缺乏“我不确定”的自省机制，而是会用极其严谨、自信且看似无懈可击的语气，编造出一个完全错误的实现。

### 2. 计算机科学的黄金原则

既然组件本身不可靠，工程上该怎么解决？计算机科学发展数十年，留下了一条黄金定律：

> **“计算机科学中的任何问题，都可以通过增加一个中间层（Middle Layer）来解决。”**

回顾整个计算机发展史，没有任何一个不可靠的核心组件，是靠“求它别犯错”来搞定的：
- 网络通信会丢包，链路无法做到绝对完美，于是有了 **TCP 协议层**（握手、重传、校验）；
- 物理硬盘迟早会坏，工业界造不出永不损坏的磁头，于是有了 **RAID 阵列与分布式备份**；
- 人类程序员一定会写错代码，没有一家公司靠“要求程序员变成神仙”来避免 Bug，而是建立了**静态类型检查、自动化测试套件与 CI/CD 质检流水线**。

工程规律惊人的一致：**对于有固定概率出错的组件，正确的解法永远是在它外面包一层！**

面对 AI 的幻觉，我们不需要幻想它有朝一日不再犯错，而是应当主动拥抱**“幻觉架构（Hallucination Architecture / Hon 架构）”**——在 Agent 生产与最终交付之间，强制插入一层独立严苛的 **Review 中间层（审查层）**。

### 3. 管理类比：实习生能直接推代码到主干吗？

任何一家规范的科技公司，都绝不可能允许新入职的实习生直接将代码提交（git push）到生产的主干分支（main）。

哪怕这个实习生是名校天才、手速极快，公司也一定会通过“权限控制分支 + 资深工程师 Code Review + 自动化流水线”这一整套**中间层机制**来约束他。

AI 就像是一个手速快你十倍、掌握所有公开语法、但缺乏公司历史业务记忆且永远盲目自信的“超级实习生”。对待他，你绝不能靠嘴上吩咐“这次你要仔细点”，而必须通过工程化的 Review 中间层把控住质量防线。

## 术语表（人话翻译）

| 术语 | 人话白话 | 生活类比 |
| :--- | :--- | :--- |
| **幻觉架构 (Hon 架构)** | 承认大模型必有幻觉，转而通过在外部包裹中间层来确保交付可靠性 | 哪怕知道防盗门锁可能被撬，在门外加装防盗报警器和监控摄像头 |
| **Review Layer (审查层)** | 夹在 Agent 产出和最终提交之间的质检关卡，只对结果负责 | 工厂流水线尽头的独立质量抽检工位 |
| **上下文独立 (Context Isolation)** | 检查者完全不看生产者的思考过程与草稿，只审查代码改动 (Diff) | 考试评卷老师只看答卷结果，不听考生考场上的碎碎念 |
| **模型独立 (Model Isolation)** | 用模型 A 生成代码，用模型 B 审查代码，利用思维盲区差异交叉质检 | 找不同医院的专家看同一张片子做二次会诊 |
| **苏格拉底式提问 (Socratic Questioning)** | 验收前主动追问反直觉的极端场景，逼迫模型跳出固有概率陷阱 | “如果明天停电一整天，你这个方案会发生什么？” |

```
       ┌───────────────────────────┐

              │             │

              ▼             └───► 打回 Agent 重新生产 (重试循环)

```

## Review 层落地的两个刚性条件

很多开发者也尝试过让 AI 审查代码，却常常抱怨：“AI 审代码根本查不出毛病，问它它都说写得挺好”。

问题出在：**你没有实现真正的“独立”**。一个合格的 Review 中间层必须满足以下两条硬指标：

### 条件一：上下文独立（Context Independence）

如果让写代码的那个会话自查，效果几乎为零。

**原因**：写代码时，AI 在该会话里经历了数十轮推理，甚至经历过多次试错。此时你在同一个会话里问：“你看看这段代码有没有漏洞？”，由于大模型的注意力机制和内在确认偏误，它会顺着自己刚才思考的逻辑去找补理由，为自己的产出辩护。

**正确姿势**：
- **剥离生产过程**：检查者绝对不能看到生产者的聊天历史和碎碎念；
- **只看结果快照**：开一个全新的独立会话，或者派生一个独立的子智能体（Sub-agent），把 `git diff` 文件的改动作为唯一输入喂给它，让它以“严苛质检官”的身份挑毛病。

### 条件二：模型独立（Model Independence）

相同模型的训练数据集相似，其概率缺陷和逻辑盲区往往高度重合。让写代码的模型自己审自己，等于让考生自己批自己的卷子。

**正确姿势**：
- **交叉双模型协作**：用 **Model A**（如 Claude Code 擅长上下文感知与大范围修改）负责敲代码编写；
- 在审查环节派发给 **Model B**（如 GPT-4o 或 DeepSeek 等其他推理模型）进行对撞质检。不同模型的底层权重和思维习惯差异巨大，交叉审查能揪出大量潜藏在盲区深处的边界漏洞。

## 固化质检标准：Skill 的力量

如果你随手丢给 Review 层一句话：“帮我审一下这段代码”，得到的回答大概率是一句毫无营养的客套话：“代码结构清晰，整体写得很好，建议注意空指针”。

必须将质检标准固化为**标准化规范清单（Skill）**。例如引入标准化的 `code-review` 技能，明确指定审查维度：

```markdown
请对照以下审查清单，严格对这段 diff 进行挑刺（未违背则通过，有违背则逐条报错）：
1. [空处理] 是否存在未被捕获的 null / undefined，是否存在空 catch 吞没异常？
2. [安全性] 是否存在 SQL 注入、越权、XSS 风险？用户输入是否有边界验证？
3. [兼容性] 是否存在未经授权删除既有函数签名或破坏老数据垫片的情况？
4. [资源泄露] 是否存在未关闭的数据库连接、未清理的定时器或内存泄漏隐患？
```

让工具去比对清单，让审查标准化、流程化。

## 实战大招：苏格拉底式提问

在所有人工审查技巧中，投入产出比最高的一招叫**苏格拉底式提问（Socratic Questioning）**。

在准备签字通过、合并代码前，在对话框里敲下这行神奇的咒语：

> **“在当前这个方案里，你究竟漏掉了什么？在极端并发或断网情况下，它会在哪一步崩溃？”**

::: tip 为什么这句话十次有九次能命中？
大模型在生成方案时，受限于贪婪搜索和上下文概率，本能地倾向于选择“平均数最高、最常见”的常规主干路径。  
当你主动抛出这句反问时，等于强制给它的注意力矩阵注入了“负反馈探针”，逼迫它从“自信论证”瞬间切换到“逆向挑错”视角。数据显示，**这种提问十次有九次能精准捞出被它顺手忽略的边缘情况或性能隐患！**
:::

## 真实报错与避坑现场

::: warning 翻车现场：自说自话的“自查陷阱”
**现场**：开发者在一个聊了 40 轮的会话里写完支付回调接口，顺口问了句：“逻辑完备吗，有没有安全漏洞？”AI 回复：“已经做了充分的签名校验，逻辑非常严谨。”上线第一天遭遇重放攻击，导致重复加款。  
**根因剖析**：同一个会话里，AI 已经认定了自己设计的“时间戳防重放”成立，无法察觉到时间窗口内没有 Redis 唯一流水锁。  
**解法**：必须开全新空白会话或派独立 Sub-agent，输入：“假设你是一个黑客，请阅读这段 diff，找到至少两种绕过支付校验实现重放加款的方法。”
:::
